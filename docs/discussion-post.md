# MoE 专家缓存实测：16 GB 显卡上的 Qwen3-Next-80B-A3B

**单机探索性性能报告 · v2.0 · 2026-10-17**

> 完整文档与原始数据见仓库 `docs/` 与 `data/`；本文是报告的 Markdown 版。

---

## 摘要

在单张 16 GB 消费级显卡上运行 80B 级 MoE 模型，专家缓存（`--moe-cache-mib`）是让解码速度可用的关键手段。本报告在同一台机器上做了三组测量：缓存是否改变输出质量、速度随缓存容量与 `ncmoe` 如何变化、不同输入类型带来多大差异。

**结论是性能层面明确、机制层面未证**：在本机与指定工作负载下，专家缓存把 decode 从 **26.806 t/s 提升到 80.673 t/s**；但为什么快、换一台机器是否同样快，本报告只给出一个尚未验证的解释，不作结论。

### 五条结论

1. **输出质量**：困惑度在四位小数内未见变化。四档 cache 0 / 512 / 2048 / 10752 MiB 均为 `4.4617 ± 0.14700`，经 `-lv 4` 探针确认缓存确实在服务专家。限定：仅 20 chunks、仅大批次路径、仅四位小数精度——不等于 bit-identical，也不覆盖 decode 路径。
2. **速度收益**：约 **3.01 倍**。decode 从 26.806 t/s（cache=0）升至 80.673 t/s（cache=10752），曲线呈 **V 型**，512 MiB 处反而低于 cache=0（20.414 t/s，−23.8%）。
3. **ncmoe 断崖**：cache 固定 10752 MiB 时，已测 6 个取值中只有 48 未出现大幅退化（80.144 t/s），44 即降至 23.639 t/s。45/46/47 未测，故 48 只代表已测范围内的最优。
4. **输入类型的影响**：真实文本 67.54–68.12 t/s，等长随机 token 93.51–93.61 t/s，相差约 **38%**。固定提示重复比多样提示快约 19%，但两组同时改变了提示内容，未分离重复性的独立效果。
5. **机制：未证实**。一个与数据自洽的解释是「cache=0 受内存带宽约束、cache>0 受 PCIe 有效带宽约束」，但它由速度与带宽常数互相反推得出，属循环推断。跨平台可复现性同样未验证。

### 本报告**不**主张什么

- **不主张「PCIe 是唯一瓶颈」**。第 4 章给的是一个与数据自洽的解释模型，它由速度与带宽常数互相反推得到。
- **不主张命中率已测得**。82.7% 是在「PCIe 跑满」假设下反解出来的数，不是日志值。
- **不主张「PPL 完全无损」**。证据只支持「四位小数、20 chunks、大批次路径内未观察到变化」。
- **不主张消费级平台可复现**。只有一台机器，跨平台部分一律写作推断。
- **不主张 48 是全局最优**。45/46/47 未测，「减小 cache + 保留静态专家」等组合也未测。

## 平台与方法

| 项目 | 值 |
|---|---|
| GPU | NVIDIA RTX 4070 Ti SUPER，16376 MiB，驱动 610.88 |
| PCIe | 4.0 x16（负载下 3 次采样均为 gen4 x16） |
| CPU | AMD Ryzen Threadripper PRO 5975WX，32 物理核 / 64 逻辑核，L3 131072 KB |
| 内存 | 4 × 32 GB DDR4-3200，4 通道（8 槽占 4 槽），全程 3200 MT/s 未降频 |
| OS | Windows Server 2025 Datacenter build 26100 |
| 引擎 | llama.cpp **b11617**（commit `14310190c`，Clang 20.1.8，CUDA 12.4） |
| 模型 | Qwen3-Next-80B-A3B-Instruct Q4_K_M（80B 总 / 3B 激活，512 专家 / 每 token 用 10 个） |

**CPU 拓扑说明（容易误读）**：所有速度测试用掩码 `0x0000000000005555`，即逻辑 CPU 0、2、4、6、8、10、12、14——按拓扑表**全部落在 CCD0**。若相邻逻辑编号互为 SMT 兄弟线程，则相当于在 CCD0 内取 8 个物理核各一个线程。**本轮测量只覆盖单个 CCD**；跨 CCD 的行为来自历史数据，不是本报告实测。

**测量协议（影响数字解读）**：每个配置启动一个 `llama-server` 进程，在其中完成 3 次计分请求；每次计分请求前后各跑一次 128-token 同提示基线用于监测漂移。**基线请求同样会改变缓存历史，因此所有数字属于带预热的协议口径，不能当作冷启动性能。**

## 结果 1：质量——困惑度在显示精度内未见变化

llama-perplexity，WikiText-2，512 ctx，20 chunks，`ncmoe 48`：

| cache (MiB) | PPL | 标准误 | 样本 |
|---|---|---|---|
| 0 | 4.4617 | 0.14700 | 20 chunks |
| 512 | 4.4617 | 0.14700 | 20 chunks |
| 2048 | 4.4617 | 0.14700 | 20 chunks |
| 10752 | 4.4617 | 0.14700 | 20 chunks |

缓存确实在生效（`-lv 4` 探针）：

```
CUDA0 MoE cache size = 10750.99 MiB for 46224.00 MiB of host experts
llama_moe_cache: large batches: 3525 experts copied from the cache, 2209.95 MiB
```

必须严格限定：证据只支持「20 chunks、该批次路径、四位小数精度下未观察到变化」，不能据此断言 bit-identical，也不能排除微小数值差异。

## 结果 2：速度曲线呈 V 型，512 MiB 是谷底

`ncmoe 48`，每配置 3 次计分请求：

| cache MiB | decode t/s | 显存 MiB |
|---|---|---|
| 0 | 26.806 | 3502–3503 |
| **512** | **20.414** | 4079 |
| 1024 | 30.001 | 4654–4672 |
| 1536 | 32.424 | 5151–5250 |
| 2048 | 35.788 | 5677–5687 |
| 3072 | 42.486 | 6681–6688 |
| 4096 | 49.222 | 7727–7732 |
| 6144 | 61.675 | 9785–9801 |
| 8192 | 69.718 | 12128–12485 |
| **10752** | **80.673** | 14749–14814 |

512 MiB 缓存比不缓存**还慢 23.8%**。与 cache=0 的平衡点落在 512–1024 MiB 之间，与文献中 prefill 侧约 1200 MiB 的 break-even 同一量级。到 10752 仍在上升，未见饱和。

## 结果 3：ncmoe 的断崖

cache 固定 10752，每配置 3 次计分请求：

| ncmoe | decode t/s | 显存 MiB | GPU util | 功耗 W | 相对 48 降幅 | 判据 |
|---|---|---|---|---|---|---|
| **48** | **80.144** | 14887–14912 | 85–86% | 77–160 | — | 否 |
| 44 | 23.639 | 15762–15830 | 95–97% | 63–92 | −70.5% | 否 |
| 40 | 19.547 | 15801–15811 | 97–100% | 63–90 | −75.6% | 部分 |
| 36 | 17.443 | 15816–15831 | 100% | 64–89 | −78.2% | 是 |
| 34 | 15.818 | 15929–15935 | 100% | 65–82 | −80.3% | 是 |
| 32 | 15.108 | 15917–15924 | 100% | 62–84 | −81.2% | 是 |

**断崖出现在已测点 48 与 44 之间，且是静默的**：无 OOM、无报错、无警告，GPU 显示很忙，功耗反而比正常低。

三特征判据（util ≥99% 且功耗 <90 W 且掉速 >25%）在这批数据上是部分自我矛盾的：把三次 run 的 `gpu_util_max` 摊开看——

| ncmoe | run1 / run2 / run3 |
|---|---|
| 48 | 85 / 86 / 85 |
| 44 | 95 / 95 / **97** |
| 40 | 97 / 100 / 97 |
| 36、34、32 | 100 / 100 / 100 |

44 **从未达到 99%**，40 只有 **1/3 次**达到。因此本报告不再用单一布尔值概括，而是分别记录降幅、显存、util 三个维度。

预算层面的解释（方向一致，但不是账本）：

```
16376 MiB 总量 − 917 桌面 = 15459 可用
cache 10752              ≈ 10751
剩余给专家层             ≈  4708  → 按每层 0.94 GB 约 4.7 层
```

该账本未计入计算缓冲、上下文与显存碎片，也未做逐层张量核对。

## 结果 4：输入类型相差约 38%

5 个独立进程 × 10 对长度匹配样本（±2 token），256 输出：

| 输入 | 标准中位数 decode |
|---|---|
| 真实文本（10 条不同 prompt） | **67.54 t/s** |
| 随机 token（等长） | **93.61 t/s** |

另一轮间隔约 1 小时的独立测量为 **68.12 / 93.51**。两组数值均为 50 样本的**标准中位数**（排序后第 25、26 个的平均）。

> 值得单独说明：llama.cpp 日志行里的 median 取的是第 26 个值（上中位数），比标准中位数系统性高约 0.2%。拿本报告数字对比自己的测量时，先确认工具用的是哪种口径。

另一个陷阱：**同一条 prompt 重复**可达 80.9 t/s，而循环 10 条不同 prompt 只有 68.0 t/s（+19%）。但两次运行同时改变了**提示内容**与**重复性**，因此不能把 19% 单独归因于重复性。

## 结果 5：环境控制

- **PCIe 链路**：负载下 3/3 采样为 gen4 x16。这只证明链路协商结果，不代表实际传输达到某个吞吐。
- **Hyper-V 干扰**：两台 VM 在部分采集时段运行。停止后复测一次，未见明显差异（约 −0.7%）。但只做了两组各一次对比，样本不足以排除小幅度影响。
- **基线漂移**：45 次基线检查中 34 次 VALID、8 次 VALID_WITH_NOTE、3 次 UNSTABLE（最大 21.03%，全部集中在最高负载档）。

## 一个未验证的解释假设

**本章不是结论**，而是把速度数字放进一个算术框架看它是否自洽。该框架由速度与带宽常数互相反推得到，本报告没有独立证据支持它。

单 token 需搬运的专家权重约 1.75 GB（由总参数/激活比例反推）：

| cache | 实测 decode | 需求带宽 | 参考上限 | 闭合度 |
|---|---|---|---|---|
| 0 | 26.806 t/s | 46.9 GB/s | 内存 ~48 GB/s（反推值） | 97.7% |
| 10752 | 80.673 t/s | 141.2 GB/s（若全不命中） | PCIe 24.45 GB/s | — |

在「PCIe 已跑满」的假设下反解得命中率约 **82.7%**。**该 82.7% 是假设的产物，不是独立测量值。**

早期版本曾把内存侧与 PCIe 侧的两次反推当作「交叉验证」，该做法不成立：两式共用同一组速度、同一组带宽常数、同一个 1.75 GB 假设，只是代数变形。**本报告明确撤回这一表述。**

要真正验证该模型，至少需要独立证据之一：DMA 基准测得的实际 PCIe 吞吐、per-token 命中率的直接日志、或逐层专家搬运账本。三者本报告均未取得。

## 实践建议

前提是「16 GB 级显存 + 大 cache + 单卡」这一类配置。

1. **在本机已测配置下，不要为了「多放几层到 GPU」而单方面降低 `ncmoe`**。cache 已占满显存时，这样做在本轮每一次测量里都表现为大幅负优化，且失效是静默的。本轮没有联合调整 cache 与静态卸载。
2. **用目标工作负载测速**。本批输入中随机 token 比真实文本快约 38%；这两个数字只对本批输入成立，但方向提示：用合成输入报数可能系统性高估真实工作负载。
3. **先确认 PCIe 宽度再谈预期**。若第 4 章的模型成立，x8 链路会使上限显著下降；幅度尚未实测，不作定量结论。

## 勘误说明

本报告由 v1.0 / v1.1 经两轮外部审核修订而来，主要更正包括：

1. **中位数取成了最大值**：脚本用 `[int](3/2)` 走银行家舍入得 2，三样本时选中最大值。已改为取排序后中间值，全部汇总重新生成。
2. **「三次独立进程」实为同一进程内三次请求**：脚本在配置循环中启动一次 server，再在进程内循环。已改述，跨进程重复性列为未验证。
3. **图 4 的中位数口径与来源标注**：原图 68.12 / 93.51 实际是 B 轮 50 样本的标准中位数，数据本身有依据，问题在于图注没有标注来源。核对中还发现旧日志的「中位数」取的是第 26 个样本，已统一为标准中位数口径。
4. **循环推断的「交叉验证」**已被明确撤回（见第 4 章）。
5. **崩塌判据**由单一布尔值改为三特征分开记录（见结果 3）。
6. **CPU 掩码描述**：`0x5555` 实际全部落在 CCD0，此前「每 CCD 取 2 个物理核」的说法有误。
