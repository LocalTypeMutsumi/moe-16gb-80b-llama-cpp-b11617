# Qwen3-Next-80B-A3B 启动配置

本目录是这台机器上跑 Qwen3-Next-80B-A3B-Instruct 的**最优参数**，来源是
`../MoE研究报告_v2.0.docx` 的实测结果。

## 用法

参数固化成了**两层**，互不冲突：

### 1. 默认层：用户级环境变量（已设置）

```
LLAMA_ARG_MOE_CACHE_MIB = 10752
LLAMA_ARG_N_CPU_MOE     = 48
```

llama.cpp 支持把任何命令行参数写成 `LLAMA_ARG_<参数名大写>` 的环境变量。
只要进程环境里有这两项，启动时**不传参数也按它来**——这就是"默认"。

已验证：不传 `--moe-cache-mib`，启动日志照样出现

```
CUDA0 MoE cache size = 10750.99 MiB for 46224.00 MiB of host experts
```

⚠️ **Windows 环境变量需要重新登录（或重启）才对新的登录会话生效**。
设置完成时已经在运行的进程（包括本机正在跑的服务）读不到，属正常。

只设这两项、不设 `LLAMA_ARG_CPU_MASK` / `LLAMA_ARG_THREADS`，是因为掩码和线程数
会影响**所有**模型；MoE 这两项在没有 MoE 层的模型上会被忽略，没有副作用。

### 2. 即时层：启动脚本（不依赖重启）

```cmd
serve-qwen3-next-80b.cmd            :: cache 10752（最优）
serve-qwen3-next-80b.cmd 8192       :: cache 8192（显存更宽松）
serve-qwen3-next-80b.cmd 6144 8081  :: 指定 cache 与端口
```

命令行参数优先级高于环境变量，所以脚本显式传参时以脚本为准，全局默认不会打架。

启动后：`http://127.0.0.1:8080`

> 注：这套环境变量只对 `E:\Apps\llama.cpp\b11617` 这套运行时有效。
> LM Studio 自带的是另一个 llama.cpp 分支，是否认 `--moe-cache-mib` 未验证。

## 固化的参数

| 参数 | 值 | 依据 |
|---|---|---|
| `--moe-cache-mib` | **10752** | 实测 80.673 t/s，是曲线的最高点（未饱和） |
| `-ncmoe` | **48** | 已测范围内唯一不崩的值；44 即掉到 23.6 t/s |
| `-C` | **0x5555** | 逻辑 CPU 0,2,4,6,8,10,12,14，**全在 CCD0** |
| `-t / -tb` | **8 / 8** | 单 CCD 8 线程；报告未测跨 CCD |
| `-lm none` | — | 与测试一致 |
| `-ngl 99` / `-np 1` | — | 全部层上 GPU、单 slot |
| `-c 4096` | — | 与测试一致 |

`0x5555` 不是"每 CCD 取 2 核"——这台机器的拓扑下它就是 CCD0 的 8 个物理核。
加 CCD 从未在这套配置上测过，所以不要把它当成"单 CCD 最优"的证据。

## 实测值 vs 报告值（重要）

| 场景 | decode | 说明 |
|---|---|---|
| 报告（干净环境，桌面占 917 MiB） | **80.673 t/s** | 测试时的状态 |
| 本次实测（桌面占 2140 MiB） | **68.6 – 70.9 t/s** | 日常桌面环境 |

差约 12%，**不是参数问题**——启动日志确认缓存拿到了完整额度：

```
offloaded 49/49 layers to GPU
CUDA0 MoE cache size = 10750.99 MiB for 46224.00 MiB of host experts
```

原因：测试时桌面只占 917 MiB，现在浏览器/微信等占了 2140 MiB，显存被挤到只剩
约 640 MiB 余量，驱动在紧张时会走共享内存路径，拖慢访问。

**想让速度回到 80+**：关掉占显存的程序再启动，把桌面占用压到 1 GB 以内。

## 为什么不用更小的缓存

同样在这台机器上做过 A/B：

| cache | decode | 显存余量 |
|---|---|---|
| 10752 | **70.4** | 674 MiB |
| 8192 | 63.2 | 3169 MiB |

降缓存损失 11%，所以宁可留紧张的显存也不降 cache。如果启动失败或运行中崩，
再降到 8192。

## 注意

- **预热协议**：报告里的数字是 warm-cache（同一进程内 3 次请求 + 前后基线）。
  冷启动单发请求会更慢。
- **输入类型影响很大**：真实多样文本约 67.5 t/s，随机 token 能到 93.6 t/s。
  别拿随机 token 的跑分当日常速度。
- **静默退化**：如果哪天速度突然掉到 20 t/s 左右、GPU 满载但功耗反而低，
  那不是过热，是显存装不下——降 ncmoe 或降 cache 都会更糟，先减缓存再看。
