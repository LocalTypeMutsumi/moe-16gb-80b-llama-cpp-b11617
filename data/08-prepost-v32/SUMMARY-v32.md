## 2. P2：显存预算扫描（ncmoe 48/44/40/36/34/32）

固定：cache 10752 / load-mode none / mask 0x5555 / t8 / max_tokens 256 / 各 3 run

| ncmoe | decode 中位 | 范围 | 显存峰值 | util | 功耗 | 判定 |
|---|---|---|---|---|---|---|
| **48** | **80.92** | 79.89–80.92 | 14887–14912 MiB | 85–86% | 77–160 W | ✅ **唯一正常** |
| 44 | 23.73 | 23.41–23.73 | 15762–15830 MiB | 95–97% | 63–92 W | ❌ 崩塌 |
| 40 | 19.58 | 19.54–19.58 | 15801–15811 MiB | 97–100% | 63–90 W | ❌ 崩塌 |
| 36 | 17.45 | 17.44–17.45 | 15816–15831 MiB | 100% | 64–89 W | ❌ 崩塌 |
| 34 | 15.84 | 15.34–15.84 | 15929–15935 MiB | 100% | 65–82 W | ❌ 崩塌 |
| 32 | 15.12 | 15.10–15.12 | 15917–15924 MiB | 100% | 62–84 W | ❌ 崩塌 |

### 结论

**崩塌分界在 ncmoe 48 与 44 之间。最优（且唯一可行）是 ncmoe 48。**

**为什么不是任务书预估的 ncmoe 34：**

任务书的算式是 `可用显存 14.5 GB ÷ 0.94 GB/层 ≈ 15 层 → 临界 ncmoe 33`。该算式**没有扣除 cache 自身占用的显存**：

```
显存总量 16376 - 桌面 917 = 15459 MiB 可用
cache 10752 占用 ≈ 10751 MiB（实测 CUDA0 MoE cache size = 10750.99 MiB）
剩下给专家层 ≈ 4708 MiB ÷ 0.94 GB/层 ≈ 4.7 层
ncmoe 48 - 4 = 44  ← 正好是实测崩塌点
```

**⇒ cache 与 ncmoe 在抢同一块显存。** 这比"预算扫描"四个字更关键：**ncmoe 一旦小于 48，就必须同时减小 cache**，否则必崩。

**三特征核对（崩塌组全部满足）**：GPU util ≥99% ✅、功耗 <90W ✅、速度掉 >25%（80.9 → ≤23.7，掉 71%+）✅

文件：`P2-ncmoe-sweep/ncmoe-*/run{1,2,3}.jsonl`、`telemetry/*.csv`、`summary.csv`

|---|---|---|---|---|

| 6144 | 61.76 | 9785–9801 | 90–91% | 76–138 W |
| 8192 | 69.84 | 见 telemetry | — | — |
| **10752** | **80.81** ← 最高 | 14887–14912 | 85–86% | 77–160 W |

### 三个判据的回答

1. **cache 512 是否比 0 慢** → **是**。26.84 → 20.42，**−23.9%**。V 型第一段存在。
2. **拐点在哪** → **512–1024 之间**。cache 1024 已超过 cache 0（30.01 vs 26.84）。与历史「约 1200 MiB」基本吻合（略偏低）。
3. **大 cache 处是否饱和** → **未见饱和**。10752 仍是最快，曲线在 8192→10752 段仍上升（69.84 → 80.81，+15.7%）。

### 形态总结（只陈述数据，不强行命名）

```
26.84 (c=0) → 20.42 (c=512, 谷底) → 30.01 → 32.43 → 35.81 → 42.50 → 49.25 → 61.76 → 69.84 → 80.81 (c=10752)
```

先降、后升、末端仍升。**斜率在 1024–4096 段最陡**。

文件：`P3-cache-curve/cache-*/run{1,2,3}.jsonl`、`telemetry/`、`summary.csv`

### ⭐ 74 vs 68 的真正解释（本轮最重要的发现）

| 测量 | 输入类型 | 结果 |
|---|---|---|
| 历史 | ? | **74.18** |
| v3.0 B | 10 条不同真实文本 | **68.34** |
| **v3.2 P5** | 10 条不同真实文本 | **67.96**（与 v3.0 几乎一致，差 0.6%） |
| **P2 ncmoe-48** | **同一条 L 文本重复 3 次** | **80.92** |
| **P3 cache-10752** | **同一条 L 文本重复 3 次** | **80.81** |

**⇒ 68 与 80.9 的差不是环境，是「输入是否重复」。**

- 同一条 prompt 反复跑 → MoE 专家缓存被反复预热 → 命中率上升 → **80.9 t/s**
- 10 条不同文本循环 → 缓存命中率低 → **68.0 t/s**
- 两者差 **+19%**

**⇒ 74.18 很可能是「重复输入/单次测量」条件下得到的**，而 68 是「多样输入」下的真实水平。

**这条必须在发帖报告里写明**：74 与 68 不可混用，它们测的是不同的东西（重复输入 vs 多样输入）。

## 6. 基线校准（v3.2 新增）

实现了**进程内首尾基线**：每个 run 在正式请求前后各跑一次 128-token 基线，计算 drift。

| drift 判据 | 计数 |
|---|---|
| VALID（<2%） | 34 |
| VALID_WITH_NOTE（2–5%） | 8 |
| UNSTABLE（>5%） | 3 |

全部记录在 `usage_log.csv`（45 行），每行含 base_before / base_after / drift / status。

**UNSTABLE 的 3 次全部集中在 ncmoe-48 与 cache-10752 这两组**（负载最高、160 W 档），其中最大一次 drift = 21.03%。

### ⚠️ 与任务书的偏离（必须声明）

任务书要求基线在**独立进程**中跑（`ncmoe 48 / cache 10752`），每个正式 run 前后各一次。字面执行意味着每个 run 要启动 3 次 server（基线/正式/基线），P2 就要 54 次启动。

**本轮实际做法**：基线在被测配置**自身的 server 内**跑（同一进程首尾各一次）。

- ✅ 能测：该配置下的进程内漂移
- ❌ 不能测：跨进程漂移、以及"基线配置与测试配置不同"带来的差异
- P5 因为沿用 v3.0 执行器（`task-b.ps1`），**没有做进程内基线**，其环境判断借用 P2/P3 的 `usage_log`

这是本轮明确的方法学折衷，报告中已标注。
